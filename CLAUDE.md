# otp-detect

Detects the one-time code (OTP) in an email: login, verification, two-factor, password reset and
transaction approval codes. Public repository, published as `@postalsys/otp-detect` once the
library exists.

## Rules

- Never use emojis in code, comments, or documentation.
- Never use em or en dashes in anything written here.
- Use Conventional Commit format for commit messages.
- **This repository is public. Never commit message content**: no `.eml` files, no labels, no
  subjects, sender addresses or extracted codes from the corpus, not even in tests, fixtures, docs
  or commit messages. Test fixtures are hand-written synthetic emails. `.gitignore` blocks `*.eml`
  and `*.jsonl` as a backstop, not as the only guard.

## Two repositories

| repo                   | visibility | contents                                                      |
| ---------------------- | ---------- | ------------------------------------------------------------- |
| `postalsys/otp-detect` | public     | library, training code, labeling prompt                       |
| `postalsys/otp-data`   | private    | OTP email subset, LLM labels, prefilter output, training sets |

The repos are checked out side by side (`~/Projects/otp-detect`, `~/Projects/otp-data`). Training
scripts take data paths as arguments and never hardcode the private repo.

The raw corpus is `~/Data/EmailCorpus/gmail-eml` (about 320k `.eml` files, personal mail). It is
read-only input; the selected emails are copied into `otp-data`.

## Library (`src/`)

`detectOtp({ subject, text, html })` takes a parsed message (no MIME parsing, no runtime deps).

- `html.ts` renders HTML to text with per-span style (font size, bold, letter spacing, link,
  hidden, quote); `doc.ts` is the shared document model and the plain text renderer.
- `candidates.ts` finds code-like tokens; `keywords.ts` holds the multilingual word lists;
  `features.ts` turns a candidate into the vector named by `FEATURE_NAMES`.
- `analyze.ts` is shared by the library and `scripts/dump-features.ts`, so training and runtime
  compute features with the same code. Never compute features anywhere else.
- `model-data.ts` is generated by `train.py` (trees in flat arrays, plus the default threshold).
  The model stores the feature names it was trained on and refuses a different list: append new
  features at the end of `FEATURE_NAMES`, then re-dump and retrain.
- Work must stay linear in the input: the input is untrusted mail. `test/index.test.ts` has
  hostile inputs; keep regexes free of unbounded scans that restart at every position.

## Data pipeline (`training/`)

Standard library Python, run with `python3 -I`.

1. `prefilter.py <corpus> <out>`: recall-oriented scan of the whole corpus (about a minute).
   Writes `candidates.jsonl` and a random `rejected-sample.jsonl` used to measure recall.
2. `label.py <in.jsonl> <out.jsonl> --model ...`: LLM labeling through the OpenAI Responses API
   with a strict JSON schema. Resumable. Returns `kind` (`otp`, `magic_link`, `other`) and the
   exact codes, each checked to occur verbatim in the text (`verified`). Key from
   `OPENAI_API_KEY` (in `otp-data/.env`, never here). The prompt defines what counts as an OTP:
   parcel locker PINs, promo, invite, ticket, meeting and EPP codes do not.
3. `select_emails.py <labels> <out>`: merges `pass1-*` and `pass2-*` label files (pass 2 wins,
   human `overrides.jsonl` win over both) into `final.jsonl` and copies the emails into `otp/`,
   `hard-negative/` and `random-negative/` in the private repo.

Labeling: `gpt-5.4-mini` over every prefilter candidate, then `gpt-5.6-sol` over everything not
confidently `other` plus a random sample of `other` rows.

## Improving the model: the scan loop

The prefilter misses some OTP emails and the hard negatives it finds are not the ones the model
gets wrong. So after training, scan the whole corpus, label every answer that is not labeled yet
with `gpt-5.6-sol` into a new `labels/pass2-sol-scanN.jsonl`, run `select_emails.py`, re-dump and
retrain. New unlabeled answers per round went 501, 244, 92, 76: the model's own mistakes are the
most useful training data.

## Evaluation

`train.py` reports per email, the way the library is used: correct, wrong code, missed, and false
positives on hard and random negatives, plus how many distinct senders the false positives come
from. Folds are `StratifiedGroupKFold` by sender domain (a service is never on both sides) and the
report is the mean of three shuffles; a single split moves by dozens of emails when one big sender
changes folds. Compare changes on these means, not on one run.

## Model design

Candidates plus a scorer, chosen over a token-tagging transformer to stay small and explainable.
The library returns the best candidate above a threshold, or nothing. A missed code is cheaper
than a wrong one: a wrong code shown to a user as "your login code" is the worst outcome.

## OTP-Token header

`draft-goto-otp-token` defines an `OTP-Token` header (structured field String with an `origin`
parameter). postal-mime parses it in `src/otp-token.ts` and exposes `message.otp = { code, origin }`.
Header first, body detection as the fallback. Do not reimplement the header parser here.
